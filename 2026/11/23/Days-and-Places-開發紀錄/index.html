Days and Places 開發紀錄

Days & Places 開發紀錄：用 Google Sheets 當行程資料庫的旅行規劃網站

Days & Places 是我為「計算機與雲端應用」做的個人專案：一個讓朋友一起規劃旅行的網站，行程資料全部放在 Google Sheets。

為什麼做這個

和朋友出遊前，行程通常散在 LINE 群組、備忘錄和好幾份試算表裡。有人改了時間，其他人沒看到；有人想知道第二天的景點在哪，得自己一個個複製去查地圖。

我想要的很單純：大家習慣的試算表照常用，另外有一個乾淨好讀的頁面，把每天的行程排成時間軸，旁邊直接對應地圖。

網站不能編輯行程，這是故意的

這個專案最重要的規則：網站不提供任何行程內容的新增、修改、刪除，不論你是擁有者、編輯者還是檢視者。行程只能在 Google Sheets 裡改，網站負責讀取和顯示。

這樣設計有三個好處：

  • 資料只有一個來源，不會出現網站和試算表各一版。
  • 朋友用最熟悉的試算表編輯，不用學新的介面。
  • 網站少了一整組寫入 API，攻擊面跟實作量都變小。

代價是每一項「防呆」都要在試算表那一端做。所以我用 Google Apps Script 幫試算表補上自動 ID、更新時間和格式檢查，也用它偵測「同一個時間出現在兩個地點」的時間衝突，網站會在該景點上顯示提醒。新增景點時，也可以直接在 map_url 欄貼上 Google Maps 連結，座標跟名稱會自動帶入。

架構與技術

瀏覽器只持有一個 Session Cookie，所有權限判斷都在後端。資料流向是：

  1. 瀏覽器呼叫 Express，後端先確認登入身分與成員角色。
  2. 使用者、旅行、成員與加入申請存在 MongoDB Atlas。
  3. 行程不存資料庫，後端透過帶 HMAC 簽章的請求呼叫 Apps Script Web App，再由它讀取 Google Sheets。
  4. 建立試算表與同步分享權限時，後端用 Owner 授權的 Google Drive API。
項目 使用
前端 HTML / CSS / JavaScript / Bootstrap 5
後端 Node.js、Express、Mongoose
資料庫 MongoDB Atlas（只存使用者與權限）
登入 Google OAuth 2.0
行程資料 Google Sheets + Google Apps Script
權限同步 Google Drive API
地圖 Google Maps URLs、Maps Embed API（選用）
部署 Render

行程資料沒有放進資料庫，是因為試算表本身就是「唯一正確的版本」。網站這邊只做短暫快取：先比對版本號，有變才重新讀取，讀取失敗時保留舊資料並標記「可能已過期」。

三種角色與加入流程

每個旅行有三種角色：

角色 網站 Google Sheets
擁有者 建立旅行、產生邀請連結、審核申請、管理成員 擁有完整權限
編輯者 唯讀瀏覽 可編輯
檢視者 唯讀瀏覽 沒有編輯權限

加入方式不是「拿到連結就能進」，而是要經過擁有者審核：

  1. 擁有者產生邀請連結，傳給朋友。
  2. 朋友開連結、登入 Google 帳號，送出申請。同一人同一個旅行不能重複申請。
  3. 擁有者在個人首頁看到待審核的申請，選擇核准為編輯者或檢視者，或拒絕。
  4. 核准編輯者時，系統同步把試算表的編輯權限給他；降為檢視者或被撤銷時，立即拿回。

被撤銷的成員必須重新申請，擁有者本人不能被移除或降級。

開發過程中踩到的坑

列被刪除時，一般的編輯觸發器抓不到。 產生 ID 和更新時間用 onEdit 就夠，但整列刪除不會觸發它，所以要再補一個 onChange 觸發器。

試算表要分享給平台帳號。 Apps Script 以平台專用的 Google 帳號執行，所以試算表要先分享給它，否則會回傳找不到試算表。我還要記住這個分享是不是系統建立的，解除連結時才不會誤刪使用者原本的分享設定。

Google Picker 顯示成一個縮成一團的視窗。 原因是內容安全政策（CSP）沒有允許行內樣式，而 Picker 需要用行內樣式定位視窗。我只放寬樣式來源，腳本來源仍然嚴格限制。

「同一個時間出現在兩個地點」這件事不能擋。 試算表可以自由輸入，所以我不阻止，改成偵測重疊後在網站上顯示警告，讓使用者自己決定。

網站權限和 Google 權限是兩件事。 Google 那邊的同步可能失敗。所以我讓網站權限優先生效，失敗的成員會標記出來，旁邊有「重試」按鈕。另外還做了「檢查並同步」，以試算表上的實際權限為準對帳，它做三件事：補發遺失的編輯權限、移除不該有的權限，只回報名單外的人，不會自動刪除。

安全上做了什麼

這個專案的原則是：密鑰不上瀏覽器，權限不信任前端。

  • 憑證只在後端。 Client Secret、Refresh Token、資料庫連線字串都不會出現在前端，也不進 GitHub。Refresh Token 用 AES-256-GCM 加密，並綁定擁有者 ID。
  • 每個旅行 API 都在後端驗證成員身分。 非成員一律回 404，不讓人從回應猜出「這個旅行存在」。
  • Apps Script 不是公開的。 每個請求都要有 HMAC-SHA256 簽章，附時間窗、一次性交易碼防重放，並確認試算表綁定在正確的旅行。
  • 邀請連結不存明文。 資料庫只存雜湊和加密後的密文，重新產生後舊連結立即失效。
  • 登入端防護。 state + PKCE、ID Token 驗證、Session 使用 HttpOnly / SameSite / Secure Cookie，再加上 helmet（CSP）和 Origin 檢查。
  • 用程式檢查規格。 我寫了一支靜態檢查腳本，確認前端沒有密鑰字串、沒有任何行程寫入路由、管理路由都有 Owner 檢查。

樣子、心得與下一步

最後我把介面改成日系文青的手帳風：和紙色底、藍染青的主色、細線框、沒有陰影，旅行卡片上貼了一小段紙膠帶，行程的連線是點線，像手帳上畫的路線。

這個專案讓我最有感的是三件事：

  • 「不做什麼」也是設計。拉掉行程編輯功能，反而讓整個系統更簡單、更安全。
  • 跨服務的權限一定會不同步，設計時要先想「失敗了怎麼辦」。
  • 把規格寫成可以自動檢查的測試，比靠眼睛確認可靠。

接下來我會把網站部署到 Render，再用兩個 Google 帳號完整走一次邀請、審核、降級、撤銷的流程。之後也想把地圖改成雙向連動，點地圖上的標記也能跳到對應的行程。
